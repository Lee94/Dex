# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Dex — an agentic data-analysis "Threads" prototype (inspired by Hex Threads). A user asks a data question in natural language; an AI agent explores a SQL warehouse, streams its step-by-step work, and answers with text + result cards. Learning/prototype.

## Monorepo layout — two standalone apps, NOT npm workspaces

`apps/agent` and `apps/web` are **independent npm projects** (each has its own `node_modules`; run `npm install` in each separately). The root `package.json` is tooling-only (Prettier, husky, lint-staged) with no `workspaces` field. `design/` holds the Claude Design handoff the UI implements — reference artifacts only (`Notebook.dc.html` informed the original app shell).

> **Product direction (v3.0):** the product is now just two concepts — **Projects** and **Threads**. A Project is a container that groups Threads and carries **shared context** (project-level instructions + bound data sources its threads inherit). The standalone **notebook** surface and all of its machinery (the cell document store, the `[cell:<id>]` editor, viz-cell persistence, cross-cell chaining) were **removed** — the agent's results are now ephemeral to the conversation (tables via `ShowSql`/`ShowSemanticTable`, charts via the visualization sub-agent rendered inline). Charts were kept but decoupled from the notebook stack.

## Commands

Root (repo-wide):

- `npm run format` / `npm run format:check` — Prettier.
- `npm run typecheck` — typechecks both apps.
- `npm run lint` — oxlint (web).
- `npm test` — runs both apps' suites (agent `node:test`, then web Vitest). **CI** (`.github/workflows/ci.yml`) runs `format:check` + `typecheck` + `lint` + agent seed/tests/smoke + web build/tests on push + PR.
- Git hooks (husky): **pre-commit** runs lint-staged (Prettier on staged files); **pre-push** runs `typecheck + lint`.

`apps/agent` (Mastra backend):

- `cp .env.example .env`, then set `ANTHROPIC_API_KEY` — required for the live LLM loop.
- `npm run seed` — (re)creates the sample `warehouse.db`. **Must be run before the agent can answer anything.**
- `npm run smoke` — exercises the SQL query layer/tools **without the LLM** (no API key needed). Quick manual data-layer check — run it after touching `db/` or `tools/`.
- `npm test` — LLM-free `node:test` suites in `test/*.test.ts` (guard, connector, semantic compiler, catalog, knowledge/memory). `pretest` re-seeds `warehouse.db`. Run with `tsx` (no extra deps).
- `npm run dev` — Mastra dev server + Studio at http://localhost:4111.
- `npm run typecheck` (`tsc --noEmit`).

`apps/web` (React + Vite UI):

- `npm run dev` — Vite at http://localhost:5173 (expects the agent on :4111; override with `VITE_MASTRA_URL`).
- `npm run build` (`tsc -b && vite build`) · `npm run typecheck` (`tsc -b`) · `npm run lint` / `lint:fix` (oxlint).
- `npm test` — **Vitest + React Testing Library** (jsdom). Config is in **`vitest.config.ts`** (separate from `vite.config.ts`, which is pinned to Vite 8 / rolldown types that clash with vitest's bundled Vite). Test files are `src/**/*.test.{ts,tsx}` — **excluded from the `tsc` build** (`tsconfig.app.json`), so they're run by Vitest (esbuild) but not typechecked.

Verification = `npm test` (both apps) + typecheck + build + lint + the agent's `npm run smoke`; CI enforces all of it (`.github/workflows/ci.yml`).

## Architecture

### Agent — `apps/agent/src/mastra/`

- `index.ts` — the `Mastra` instance. Registers the agent under the key **`analyst`** (this exact key is how the web client addresses it), with a LibSQL store, permissive CORS for the Vite origin, an env-configurable `PinoLogger` level (`LOG_LEVEL`), and AI tracing via `buildObservability()` (see `observability.ts`).
- `agents/analyst.ts` — the data-analyst agent: instructions + model + its toolset + Mastra `Memory`. Its instructions tell it to **prefer the semantic model** and fall back to raw SQL for the long tail; they're dialect-aware (SQLite vs Postgres). Its **instructions are a dynamic async function** (v0.9): the static prompt plus the live saved memories + available guide titles, re-evaluated each turn. Tools grew well past the original six: semantic discovery (`FindSemanticColumns`/`InspectSemanticData`), raw-SQL discovery (`FindTableSchemas`/`ViewTables`), **user-visible results** (`ShowSql` runs a query and shows its table; `ShowSemanticTable` does the same from the semantic layer; `RunSQL` is the ephemeral scratchpad), catalog/clock (`ListDataConnections`/`GetCurrentDateTime`, v0.8), knowledge/memory (`ReadGuide`/`SaveMemory`/`SuggestReview`, v0.9), external context (`SearchWeb`/`ExtractWeb`/`GetFileContents`, v1.1), scheduling/recall (`CreateTask`/`ViewTask`/`ReadPastThreadSummary`, v1.3), and **delegation** to the specialist sub-agents (`DelegateToDataDiscoveryAgent`/`DelegateToVisualizationAgent`, v1.2). Results are referenced inline with **`[result:<id>]`** (no persistence — the id is just an embed handle for the conversation).
- `agents/discovery.ts` + `agents/visualization.ts` — the v1.2 **specialist sub-agents**. `dataDiscoveryAgent` owns the read-only discovery tools and returns a discovery brief; `visualizationAgent` (no data tools) authors a vinci chart DSL via **`build_chart`** (which only validates + returns the spec — no persistence). They're **internal**: registered in the `Mastra` instance for full context (logger/tracing) but the web never addresses them — only the analyst delegates via its delegation tools, then synthesizes. The delegation tool lifts the built chart(s) (`{cellId, dsl, sourceOutputName}`) out of the sub-agent run so the thread renders them over the upstream result's rows. The `analyst` key + stream contract are unchanged.
- `model.ts` — resolves the agent's language model from env. Supports two wire protocols plus a preset, each selectable via `LLM_PROVIDER` (`anthropic` | `openai` | `deepseek`) or inferred from whichever API key is set (Anthropic wins ties): **`anthropic`** (`@ai-sdk/anthropic`), **`openai`** (`@ai-sdk/openai-compatible` — OpenAI/DeepSeek/OpenRouter/vLLM/Ollama/…), **`deepseek`** (`@ai-sdk/deepseek`). Each takes a custom `*_MODEL_ID` and `*_BASE_URL`. Every provider is used via its AI SDK package **directly**; do NOT switch to Mastra's `'provider/…'` model-router string — it routes through a models.dev gateway that fails in offline/restricted environments. For Anthropic it also normalizes `ANTHROPIC_BASE_URL` to end in `/v1` (some environments, including Claude Code's, set it without the suffix, which makes requests 404). Exports the resolved `model` (hand straight to the `Agent`), plus `PROVIDER` / `MODEL_ID` for display. See `.env.example` for all knobs.
- `observability.ts` — AI tracing setup (`@mastra/observability`). `buildObservability()` returns a configured `Observability` (handed to the `Mastra` constructor's `observability` field) or `undefined` when `DEX_OBSERVABILITY=off`. With it wired in, Mastra **automatically** emits a span tree per request — `agent:analyst run → llm (model/tokens/latency) → tool:* (I/O/timing)` — with **no** instrumentation in the tools or data layer. Two zero-dependency exporters, no external backend: `MastraStorageExporter` (always on → writes to `mastra.db`, browsable in **Mastra Studio** at :4111) + `ConsoleExporter` (terminal, default on, off via `DEX_TRACE_CONSOLE=false`). `serviceName` = `OTEL_SERVICE_NAME` (default `dex-analyst`). Mastra auto-applies a `SensitiveDataFilter`, so secrets in span payloads are redacted before export. To export to an external backend (SigNoz/OTLP), you'd add a `BaseExporter` subclass — there's no built-in OTLP exporter in this version.
- **Warehouse data layer (connector seam, v0.3).** Queries go through a `Connector` interface so the agent can target the bundled SQLite sample _or_ a live Postgres warehouse without the tools/UI changing:
  - `db/types.ts` — shared types + the `Connector` interface (`listTables` / `describeTable` / `runReadOnlySql`).
  - `db/guard.ts` — `assertReadOnly` (single statement, must start SELECT/WITH, rejects DML/DDL) + `IDENTIFIER`. The **universal** gate; runs before any SQL executes.
  - `db/connectors/sqlite.ts` (default) + `db/connectors/postgres.ts` (`pg`; `information_schema` introspection, read-only transaction + `statement_timeout` + row caps as defense in depth).
  - `db/connector.ts` — `getActiveProvider()` / `getConnector()` (lazy, cached) resolve the active connector from env (`WAREHOUSE_PROVIDER` = `sqlite` | `postgres`, else inferred from `DATABASE_URL`/`PGHOST`); `dialectHint()` feeds the agent dialect-specific syntax.
  - `db/queries.ts` — now a thin **façade** that delegates `listTables`/`describeTable`/`runReadOnlySql` to the active connector and re-exports the guard + types (keeps the old import surface for the tools/smoke).
- **Semantic layer (CubeJS-style, v0.4; dynamic models v0.7) — `db/semantic/`.** A typed model + a query→SQL compiler: `types.ts` (cubes/measures/dimensions/joins/metrics + the semantic-query shape), `model.ts` (the built-in sample model; **endorsed** metrics like `revenue`/`completed_revenue`), `compile.ts` (member resolution, BFS join-path planning, dialect-aware time grains, escaped filter values), `validate.ts` (structural checks, run at load), `index.ts` (`runSemanticQuery` = compile → `assertReadOnly` → connector; plus the catalog/summary builders). The compiled SQL **never bypasses** the read-only guard.
  - **User-defined models (v0.7) — `db/semantic/store.ts`.** Beyond the hand-authored built-in cubes, the UI can add/remove extra cubes ("data models") at runtime; they persist as JSON in `dex.db` (`dex_semantic_models`). `loadMergedModel()` (in `index.ts`) appends them onto the built-in cubes (skipping any that collide by name or fail `validateModel`, so a bad row can't break the model). `runSemanticQuery` and the **async** summary builders (`describeModelSummaryAsync`/`listMetricsCatalogAsync`) run over the merged model, so user cubes are queryable by the agent, not just visible in the UI. User cubes are standalone (no joins) and never `endorsed`.
- `tools/*.ts` — thin `createTool` wrappers. SQL tools: `list_tables`, `describe_table`, `run_sql` — each takes an **optional `datasourceId`** and resolves its connector via `getConnectorById(datasourceId ?? 'builtin')`, so the agent can query a registered non-builtin source on demand (default = the env active source). `list_tables`/`describe_table` also return the queried source's `dialect`. Semantic tools: `list_metrics`, `describe_model`, `query_semantic` (over `db/semantic`; `list_metrics`/`describe_model` use the **async merged-model** variants so user-defined cubes are visible to the agent). Note: in this Mastra version, `createTool`'s `execute` receives the parsed input as its **first argument**. A `query_semantic` result carries `via:'semantic'`, the compiled `sql`, and an `endorsed` flag the UI surfaces.
- `db/warehouse.ts` (libsql client for the SQLite connector) + `db/seed.ts` (sample e-commerce schema: customers/products/orders/order_items).
- **Data-source module (v0.6) — `server/routes.ts` + `db/datasources.ts` + `db/metadata.ts`.** Read-only catalog/connection HTTP routes registered on the Mastra server (`registerApiRoute`, wired via `server.apiRoutes` in `index.ts`). They mount at the server **root** (`/datasources`, `/datasources/:id/tree|tables/:t|.../preview`, `/datasources/:id/metadata`, `/semantic/projects…`) — **not** under `/api` (where the agent's own routes live). They're independent of the agent (sidestepping the boot-time dialect constraint): `connector.ts` keeps the env singleton and adds a `Map<id,Connector>` (`createConnectorFromConfig`/`getConnectorById`/`closeConnectorById`); both connectors gained an optional parameterized constructor. Preview is `SELECT * … LIMIT n` through `runReadOnlySql` (so the guard + PG defenses apply); table names pass `IDENTIFIER`. Credentials never enter the DB — see `dex.db` below. **Mutations (v0.7):** `DELETE /datasources/:id` removes a connection (builtin → 409); `POST`/`DELETE /semantic/projects/:projectId/models[/:modelId]` add/remove a user model (a built-in model → 404 on delete; `buildUserCube` validates the base table + columns exist in the builtin warehouse before persisting).
- **Projects module (v3.0) — `server/project-routes.ts` + `db/projects.ts`.** Root REST routes (`GET`/`POST /projects`, `GET`/`PATCH`/`DELETE /projects/:id`) over a `dex_projects` table (name, description, instructions, attachments JSON, resource-scoped). A project is just a container + shared context; **thread membership is NOT stored here** — a thread records its `projectId` in its Mastra thread `metadata`, so a project's threads are listed with a metadata-filtered memory query (web `listProjectThreads`). Independent of the agent stream.
- **More root route modules** wired the same way in `index.ts` (`server.apiRoutes`): `knowledge-routes.ts` (v0.9 `/guides` + `/memories` + `/reviews`), `upload-routes.ts` (v1.1 `/uploads`, base64 JSON), `task-routes.ts` (v1.3 `/tasks` CRUD + `/tasks/:id/run` + `/thread-summaries`). Each backs a web surface and stays independent of the agent stream.
- **Scheduler (v1.3) — `db/scheduler.ts` + `db/task-runner.ts` + `db/cron.ts`.** An in-process ticker started from `index.ts` (gated by `DEX_SCHEDULER`, `unref`'d) runs due `dex_tasks` on a cron: `task-runner.ts` resolves a task to its read-only SQL, runs it through `runReadOnlySql`, evaluates the alert, and delivers via the mockable `db/delivery.ts` seam (Slack/webhook). Tasks are **SQL-only** (the v2.0 notebook-cell task kind was removed in v3.0). `cron.ts` is a dependency-free 5-field matcher. All LLM-free and unit-tested.

There are now three SQLite files, all gitignored: **`warehouse.db`** = the sample data the agent queries; **`mastra.db`** = Mastra's own conversation/telemetry storage (v0.2 thread persistence); **`dex.db`** = Dex's own store, anchored next to `warehouse.db` via `db/store.ts`. `dex.db` grew with the agent: `dex_datasources` (v0.6 registry) + `dex_table/column_metadata` (v0.6 overlay) + `dex_semantic_models` (v0.7 user cubes) + `dex_guides`/`dex_memories`/`dex_review_requests` (v0.9 knowledge/memory/review) + `dex_uploads` (v1.1 files, base64, size-capped) + `dex_tasks`/`dex_thread_summaries` (v1.3 scheduling + recall) + `dex_projects` (v3.0 project containers + shared context). (The v2.0 `dex_notebooks` table was retired in v3.0.) Each store module owns its `CREATE TABLE IF NOT EXISTS` (lazy `ensureSchema`). Data-source **secrets** (password / connection string) live only in a gitignored `datasources.local.json`, never in any DB; the registry row keeps a `credentialRef`.

### Web — `apps/web/src/`

- Implements the Blueprint-styled "Dex" design from `design/`. **Navigation is URL-routed** via react-router v7 (`router.tsx` = `createBrowserRouter`, mounted by `RouterProvider` in `main.tsx`) — the old `App.tsx` view-state-machine is gone. Routes are deep-linkable: `/` → `/threads`, `/threads/:id` (full-screen, rendered **outside** the Shell), `/projects` + `/projects/:id`, `/data/:connId?/:table?`, `/knowledge`, `/tasks`, and placeholder routes for the unbuilt nav items. Nested layouts live in `layouts/`: `RootLayout` mounts `useThreads` **and `useProjects`** once (via `contexts/ThreadsContext.tsx` + `contexts/ProjectsContext.tsx`) so the thread list, in-flight streams, **and the project list survive navigation**; `ShellLayout` is the sidebar + `<Outlet/>` chrome. Thin route wrappers live in `routes/` (`ThreadRoute`, `ThreadsListRoute`, `ProjectsListRoute`, `ProjectRoute`); the heavy surfaces (DataBrowser, Knowledge, Tasks, Projects, ThreadView) are code-split via **route-level `lazy`**. `Sidebar.tsx` uses `NavLink` (active state derived from the URL); the active thread / project / connection / table is read from `useParams` (no more `localStorage` activeId).
- **Projects (v3.0) — `components/projects/` + `hooks/useProjects.ts` + `contexts/ProjectsContext.tsx` + `lib/projects.ts`.** `/projects` is a grid of project cards (`ProjectsList`); `/projects/:id` (`ProjectDetail`) edits the name/description, the **shared context** (project-level instructions + bound data sources, reusing `ContextPicker`), and lists/launches the project's threads. `useProjects` mirrors `useThreads`' lazy-load + optimistic CRUD over `lib/projects.ts` (the root `/projects` REST routes). A thread's project is set on creation (`createThread(projectId)`) and persisted to its Mastra metadata on the first message (`updateThreadMeta`).
- **Data-source module (v0.6; mutations v0.7) — `components/data-browser/` + `hooks/useDataBrowser.ts` + `lib/dataSources.ts`.** Implements `DataBrowser.dc.html`: source list + Add-connection dialog, schema/table tree, table columns + real-row preview, semantic-model browsing, and metadata curation (description/status/categories/Included-for-AI, optimistic). **v0.7 adds management:** delete a connection (hover-revealed trash on non-builtin `SourceList` rows → `ConfirmDialog`), and add/delete a data model (`AddModelDialog` picks a base table → measures/dimensions; delete on user model cards + `ModelDetail`). `lib/dataSources.ts` talks to the agent's **root** REST routes with `fetch` (MastraClient only does agent-stream + memory); the hook mirrors `useThreads`' lazy-load + optimistic-update pattern. Reuses `--dex-*` tokens (+ a few new `--dex-conn-*`/`--dex-type-*`/`--dex-logo-purple` tokens) and `components/ui` primitives (incl. the new reusable `ConfirmDialog`).
- **Composer data context (v0.7; project context v3.0) — `components/Composer.tsx` + `components/ContextPicker.tsx` + `lib/attachments.ts`.** The composer's "+" opens a popover (`ContextPicker`) to attach a **database / table / model** to the next question; attachments render as removable chips and are folded into the sent message by `contextPrefix()` (a short "Focus on…" preamble). **v3.0:** `contextPrefix(attachments, project?)` also folds a project's **shared context** (its instructions + bound data sources) into the preamble; `ThreadView` passes the project only on the thread's **first message** (memory replays it for the rest of the conversation). `splitUserMessage` strips the preamble for display, surfacing a "Project: …" chip. For a **non-builtin** source/table the preamble carries the `datasourceId` + dialect and instructs the agent to pass that id to its SQL tools — so an attached table from another registered database is **actually queryable**, not just a hint (a builtin attachment uses the default warehouse). Each attachment therefore carries `sourceId`/`dialect`/`builtin`. The picker reads the same root REST routes via `lib/dataSources.ts`; no changes to the agent stream contract.
- **Agent stream wiring** is the heart of the app: `hooks/useThreads.ts` calls `analystAgent.stream(messages, { memory: { thread, resource } }).processDataStream({ onChunk })` and maps Mastra stream chunks onto UI state — `text-delta` → the answer; `tool-call`/`tool-result` → the collapsible "thinking" step timeline; a `ShowSql` / `ShowSemanticTable` result (shape-detected by `isSqlResult` in `types.ts`) → a `ResultCard` (table); a chart from the visualization sub-agent → `components/thread/ThreadChart.tsx` (the read-only vinci viewer, decoupled from the old notebook stack). `ThreadView` resolves inline `[result:<id>]` embeds against the same-turn tool results. `resultProvenance()` reads a semantic result's compiled `sql` + `endorsed` flag so the card can show a **"Trusted definition"** pill. Streaming is soft-stoppable.
- **Persistence (v0.2) — `lib/threads.ts`.** Threads live in Mastra memory (`mastra.db`) keyed by a stable `threadId` + a single-user `RESOURCE_ID`. This module lists threads, lazy-loads a thread's history, renames/deletes, and **reconstructs** the thinking timeline + result cards from stored message parts. `useThreads` loads the list on mount and hydrates messages on open; the active selection now lives in the **URL** (`/threads/:id`), not `localStorage`. The sidebar recents + threads list are real (rename/delete + empty/loading/error states).
- `lib/mastraClient.ts` — `MastraClient` pointed at `config.mastraBaseUrl`; `analystAgent = mastra.getAgent('analyst')`.

### Styling system (important)

CSS Modules over a token layer — **do not hardcode hex/rgba in components.** `src/index.css` imports the vendored Blueprint tokens (`src/blueprint/`) then `src/styles/theme.css`, which defines `--dex-*` semantic tokens mapping the design's literal values onto Blueprint `--bp-*` vars. Each component has a co-located `*.module.css` referencing those vars; reuse the primitives in `components/ui/` (IconButton, Button, Pill, Avatar). Imports use the `@/` path alias (`@/* → src/*`).

## Conventions & gotchas

- Two apps, no workspaces → install and run each app separately.
- Web↔agent contract: the agent must stay registered as `analyst`, and the web client streams from the Mastra dev server (:4111). Renaming the agent key requires updating `getAgent('analyst')` and the registry key in `index.ts`.
- Web routing: the URL is the single source of truth for navigation. The long-lived hooks (`useThreads`, `useProjects`) are mounted in **`RootLayout`** above `<Outlet/>` so their state — including live agent streams + the project list — survives route changes; **don't** pull them down into leaf route components. Read the active id from `useParams`, never localStorage. The full-screen `/threads/:id` route sits outside `ShellLayout` (no sidebar) — keep that split if you add thread sub-routes.
- Thread ↔ project membership lives in **Mastra thread metadata** (`{ projectId }`), not a join table. `lib/threads.ts` `updateThreadMeta` is the single writer — it **replaces** metadata, so always pass the intended `projectId` alongside the title (a bare rename would otherwise wipe the project). List a project's threads via the metadata filter (`listProjectThreads`).
- Read-only SQL only: any new query path must go through `assertReadOnly` (`db/guard.ts`) — including compiled semantic SQL.
- New warehouse backends plug into the `Connector` interface (`db/types.ts`); don't query a driver directly from the tools. Point Dex at Postgres via env (see `.env.example`); never commit credentials.
- The **built-in** semantic model is a typed config (`db/semantic/model.ts`) validated at load — add measures/dimensions/joins/metrics there; the compiler and tools pick them up automatically. **User-defined** models are runtime data (`dex_semantic_models` in `dex.db`, via `db/semantic/store.ts`) merged in by `loadMergedModel()`; anything that reads the model at runtime must use the merged/async variants (`runSemanticQuery`, `describeModelSummaryAsync`, `listMetricsCatalogAsync`), not the static `model`/`describeModelSummary` (those stay built-in-only for the sync `compile`/smoke path).
- After changing the warehouse schema/seed, re-run `npm run seed` then `npm run smoke` (smoke now also covers the connector interface + the semantic compiler).
- `src/blueprint/` and `design/` are vendored / handoff artifacts — don't edit or reformat them (they're in `.prettierignore`).
