# v2.0.0 — NotebookEditor 🚧 In progress (core shipped)

**Theme:** Dex becomes a **notebook**, not just a thread chat. Implement the
cell-based editor — the milestone the project was scoped toward from day one, and
the first major leap past the 1.0 product.

## Status — core shipped

The cell-based core landed: a notebook surface (list + editor) with **SQL cells**
you can create / edit / reorder / delete / **re-run**, persisted in `dex.db`
(`dex_notebooks`), with results rendered via the v0.5 result cards. The **Hex
agent model** is wired end-to-end: the analyst authors cells into a thread's
notebook (`notebook id = threadId`) via **`create_sql_cell`**, inspects them with
**`read_cells`**, chains them by **`outputName`** (CTE flattening, cycle-checked),
and embeds outputs in its answer with **`[cell:<id>]`** (Hex visibility —
`run_sql` stays an internal scratchpad, cells are what the user sees). A thread
opens **"as a notebook"** for editing. A confidentiality rule mirrors Hex's
"what I can't share."

**The rest of the notebook track is deferred to the back** (Thread mode is the
current focus): richer cell types + cell ops →
[v2.1](./v2.1.0-richer-cells.md); charts as cells →
[v2.2](./v2.2.0-charts-and-viz.md); Python/dataframe kernel →
[v2.3](./v2.3.0-python-kernel.md). The near-term **Thread-mode agent** track
(catalog, guides/memory, web/files, sub-agents, scheduling) is v0.8–v0.9 and
v1.1–v1.3.

## Goal

Dex becomes a **notebook** — an editable, re-runnable, **cell-based document** the
user and the agent co-create, over the same read-only engine as Thread mode.

## Why

v0.1 deliberately shipped the `Notebook.dc.html` surface (shell + threads + live
thread chat) and **deferred** the larger `NotebookEditor.dc.html`. With persistence
(v0.2), real data (v0.3), a CubeJS-style semantic layer (v0.4), richer results
(v0.5), and a tested, CI-backed 1.0 foundation (v1.0) in place, the project is
finally solid enough to build the headline experience: an editable, re-runnable,
cell-based notebook where the user and the agent co-create the analysis.

## Scope

- **Implement `design/hex-tech/project/NotebookEditor.dc.html`** — the cell-based
  editor UI, styled with the existing `--dex-*`/Blueprint token system and `ui/`
  primitives (no hardcoded hex; reuse, don't re-invent).
- **Cells** — at least **SQL**, **text/markdown**, and **chart/result** cell
  types; create, edit, reorder, delete, and **re-run** individual cells.
- **Agent ↔ notebook** — promote a thread's agent steps into editable cells (or
  let the agent author/append cells), so an exploration becomes a durable,
  tweakable document rather than a transcript.
- **Execution model** — run a cell (or the notebook) through the same read-only
  query path + connectors (v0.3) — raw SQL or a v0.4 semantic query — and render
  results via the v0.5 result cards.
- **Persistence** — notebooks save/load/rename/delete on top of the v0.2 store.
- **Threads ↔ notebooks** — a clear relationship (open a thread as a notebook /
  start a notebook from a thread).

## Out of scope

- The **Canvas** surface (`design/hex-tech/project/Canvas.dc.html`) — a sibling
  free-form board; stays in the icebox.
- Real-time multi-user co-editing, comments, and sharing — later (post-2.0).
- A plugin/extension system for custom cell types.

## Technical notes

- This is the largest milestone — expect to revisit the web app's view-state
  machine (`App.tsx` currently switches `threads | thread | notebook | other`) and
  introduce real notebook/cell models in `types.ts`.
- Reuse everything earned earlier: result cards (v0.5), connectors + read-only
  guard (v0.3), the semantic layer (v0.4), persistence (v0.2), tests + CI (v1.0),
  and the streaming/soft-stop wiring (v0.1).
- Keep the web↔agent contract intact — the `analyst` agent and the Mastra stream
  remain the execution backbone; cells are a new surface over the same engine.
- Land it incrementally behind the existing view state (e.g. read-only notebook
  render first, then editing, then per-cell re-run).
