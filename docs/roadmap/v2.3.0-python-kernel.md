# v2.3.0 — Python & dataframe kernel 📋 Planned

**Theme:** Add a sandboxed **Python/duckdb kernel** — unlocking Python cells,
dataframe-mode SQL, and cross-source chaining.

## Goal

Add a sandboxed **Python/duckdb kernel** — unlocking **Python cells**,
**dataframe-mode SQL**, and **cross-source chaining**.

## Why

Several Hex capabilities — `CreatePythonCell`, dataframe-mode `CreateSqlCell`,
and chaining across connections — assume a kernel where each cell's output is a
**dataframe**. Dex has none, so chaining is same-source CTE flattening only and
there is no Python. This is the platform bet that lifts those limits.

## Scope

- **Kernel** — a sandboxed Python/duckdb runtime; a cell's output becomes a named
  dataframe other cells can reference.
- **`create_python_cell`** (Hex `CreatePythonCell`) — run Python over upstream
  dataframes.
- **Dataframe-mode SQL** — duckdb SQL over dataframes/files; **cross-source
  chaining** (a warehouse result → dataframe → joined with another source).
- **`queryMode`** — keep large warehouse outputs in the warehouse instead of
  materializing them locally.

## Out of scope

- **Arbitrary package install / outbound network from the kernel** — sandbox
  limits.
- **GPU / heavy compute.**

## Technical notes

- The biggest infra change in the roadmap. The execution seam (today
  `runReadOnlySql` + `resolveChainedSql`) gains a kernel path; **sandboxing /
  resource limits are the central concern**. The read-only guard still gates all
  warehouse SQL; kernel code runs isolated.

## Acceptance criteria

- [ ] A **Python cell** runs over an upstream cell's dataframe in a sandbox.
- [ ] A **dataframe-mode SQL** cell joins **two different sources**.
- [ ] Large outputs can stay **query-mode** (not materialized into the kernel).
- [ ] The sandbox enforces resource/network limits; warehouse SQL still passes
      `assertReadOnly`.
- [ ] **Verification green:** both apps `typecheck`; the kernel path is covered by
      tests/smoke.
