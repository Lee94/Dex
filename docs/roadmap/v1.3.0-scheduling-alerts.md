# v1.3.0 — Scheduling & alerts ✅ Shipped

**Theme:** Run analyses on a **schedule** and **deliver / alert** — plus recall
across past threads. (This was the roadmap icebox item "Scheduled refreshes &
alerts.")

## Goal

Turn a saved thread/notebook into a **living artifact** — scheduled re-runs with
delivery and alerts, plus recall across past threads.

## Why

Hex can schedule recurring runs with email/Slack delivery and recall past-thread
summaries. Dex runs only interactively. This makes a saved thread/notebook a
**living, delivered** artifact instead of a one-off.

## Scope

- **`create_task` / `view_task`** (Hex `CreateTask` / `ViewTask`) — schedule a
  thread/notebook to re-run on a cron; **deliver** results via email/Slack;
  **alert** on a change/threshold.
- **`read_past_thread_summary`** (Hex `ReadPastThreadSummary`) — pull context
  from prior threads.
- **Tasks UI** — list / create / disable scheduled runs.

## Out of scope

- **A full alerting rules engine** — start with simple thresholds.
- **Multi-tenant scheduling** (depends on multi-user/auth — icebox).

## Technical notes

- A scheduler (cron) + delivery integrations; re-runs go through the same
  read-only execution path; tasks persist in `dex.db`.

## Acceptance criteria

- [x] A read-only query (or notebook cell) can be **scheduled to re-run on a cron**
      and **delivers** its result (Slack / generic webhook; email deferred — needs
      SMTP).
- [x] An **alert fires** on a configured threshold/change (gt / lt / ne / changed).
- [x] **`read_past_thread_summary`** lets the agent recall a prior thread's
      summary (recorded by the web on thread completion).
- [x] **Verification green:** tasks persist in `dex.db`; re-runs go through the
      read-only execution path (`runReadOnlySql`); `npm run smoke` + `node:test`
      cover task CRUD, the cron matcher, the alerting + delivery seam, and recall.
