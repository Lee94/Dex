# v0.7.0 — Data management ✅ Shipped

**Theme:** Turn the read-only Data browser (v0.6) into something you can _manage_,
and let a question target specific data. Three additions: **delete a data
connection**, **add / delete a data model** (the semantic layer becomes editable
from the UI), and a composer **"+" picker** to attach a database / table / model
to the next question.

## Goal & why

v0.6 made data sources and the semantic model _visible_ — a catalog you could
open, drill, and annotate — but it was read-only in two telling ways: a
registered connection could not be removed from the page, and the semantic model
stayed a hand-authored typed config (explicitly out of scope for v0.6). This
milestone closes both gaps so the catalog is a managed asset, and adds the
missing bridge between the catalog and a thread: pointing a question at a chosen
database, table, or model from the composer.

## Scope

- **Delete a connection.** A hover-revealed trash on each non-builtin source row
  → a confirm dialog → `DELETE /datasources/:id` (the route already existed; v0.7
  surfaces it). The env-configured `builtin` source can't be deleted (409).
- **Add / delete data models.** A model ("cube") over a base table in the agent's
  warehouse: pick a table, name it, choose **measures** (count / sum / avg /
  count_distinct / min / max) and **dimensions** (groupable columns). User models
  persist in `dex.db`, merge onto the built-in cubes, and are **queryable by the
  agent** (not just browsable). Delete is available on user models only.
- **Composer "+" context.** The composer's "+" opens a popover to attach a
  database, table, or model; attachments show as removable chips and are folded
  into the sent message as a short "Focus on…" preamble. When the attachment is a
  table/source from **another registered database**, the preamble carries its
  `datasourceId` + dialect and the agent's SQL tools take an optional
  `datasourceId` — so the attached table is **actually queryable**, not just a
  hint. (A builtin attachment uses the default warehouse.)

## Out of scope

- **Editing an existing model in place.** Models are add/delete only; to change
  one, delete and recreate. (Metadata curation on tables/columns from v0.6 is
  unchanged.)
- **Joins / metrics on user models.** A user cube is standalone (no joins) and
  un-endorsed; its measures are queryable as `cube.measure` but it contributes no
  top-level named metrics. The built-in model keeps its joins + endorsed metrics.
- **User models over a non-builtin source.** Compiled semantic SQL (the semantic
  layer) runs against the agent's (builtin) warehouse, so a _model's_ base table
  must exist there. Raw SQL via `run_sql` **can** target another source by
  `datasourceId` (see the composer "+"); only the semantic compiler is
  builtin-only.
- **Switching the agent's _default/active_ source at runtime.** The agent's
  primary warehouse + boot-time dialect are still env-fixed (a restart concern).
  New in v0.7: the agent can _additionally_ query any registered source per
  tool-call via `datasourceId` — but the default target is unchanged.

## Technical notes

- **Dynamic semantic model.** `db/semantic/store.ts` persists user cubes as JSON
  in `dex.db` (`dex_semantic_models`). `loadMergedModel()` appends them onto the
  built-in cubes, **skipping** any that collide by name or fail `validateModel`
  (a bad row can't take down the model or the agent). `runSemanticQuery` and the
  new async summaries (`describeModelSummaryAsync` / `listMetricsCatalogAsync`)
  run over the merged model; the agent's `describe_model` / `list_metrics` tools
  use them, so user cubes are visible to the agent. The sync `compile` / built-in
  `describeModelSummary` stay built-in-only for the smoke path.
- **New routes, same patterns.** `POST` / `DELETE
/semantic/projects/:projectId/models[/:modelId]` on the server root.
  `buildUserCube` validates the base table + every measure/dimension column
  exists in the builtin warehouse (via `describeTable`), and rejects a name that
  collides with any existing cube (409). Deleting a built-in model → 404.
- **Never bypass the guard.** A user model compiles to ordinary semantic SQL that
  still passes `assertReadOnly`; member names go through the same model-validated
  path (no injection), base-table/column names through `IDENTIFIER`.
- **Reuse over rebuild.** Web adds a reusable `components/ui/ConfirmDialog`,
  `AddModelDialog`, and `ContextPicker`; the composer folds attachments via
  `lib/attachments.ts` (`contextPrefix`) with **no change to the agent stream
  contract**. `npm run smoke` covers create → merge → query → delete of a user
  cube.

## Done when

- A non-builtin connection can be **deleted** from the Data browser (with a
  confirm); the builtin source cannot.
- A **new data model** can be created over a warehouse table (measures +
  dimensions), shows in Data Models, is **queryable by the agent**, and can be
  **deleted**; built-in models cannot be deleted.
- The composer **"+"** attaches a database / table / model as chips that scope the
  next question; an attached table from **another registered database** is
  actually queryable by the agent (via `datasourceId`), not just a text hint.
- `npm run smoke` passes (existing assertions unchanged + the new user-model
  checks); typecheck + lint + build (web) are green.
