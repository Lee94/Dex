# v3.1.0 — Interactive result grid 📋 Planned

**Theme:** Turn the static result table into an interactive data grid — the
single biggest gap vs. Hex's result experience, and the highest-ROI step because
it's almost entirely front-end and doesn't touch the agent stream contract.

## Why

Today a `ShowSql` / `ShowSemanticTable` result renders as a plain, read-only
`<table>` (`components/ResultCard.tsx` → `DataTable`): no sorting, no filtering,
no pagination (rows hard-truncate), and the "Maximize" button has **no handler**.
Hex's result is a real data grid (sort, filter, search, column stats, virtual
scroll, conditional formatting). After the agent answers, the user can't explore
the data at all — analysis dead-ends at the first table.

Several buttons are also rendered but inert and read as "broken": result-card
**Maximize** (`ResultCard.tsx:114`), header **Share** / **Translate**
(`ThreadView.tsx:115,123`), composer **cog** / **Auto** (`Composer.tsx:110,118`).

## Approach — reuse vinci's table, don't hand-roll a grid

vinci already ships table rendering on the **same compile pipeline** the thread
chart uses (`vinci/compileSurface.ts` → `snapshot/table/api` → `VinciViewer`):

- `chartType: "detail"` — a flat detail table (see `vinci/dsl/examples/detail.surface.json`).
- `chartType: "cross"` — a pivot/cross-tab with sub/grand totals
  (`crossTotals.surface.json`).
- DSL-level sort (`dsl/registry/sort.ts`, viewer already gets `supportNoneSortType`),
  filter (`dsl/registry/filter.ts`), and conditional formatting (`conditionFormat.ts`).
- `@vinci/designer` (already a dependency, **currently unused**) bundles
  `@tanstack/react-virtual` (virtual scroll) and pragmatic-drag-and-drop.

So the **inline default stays the lightweight HTML table** (it renders for every
result and the vinci stack is heavy — that's why `ThreadChart` is `lazy()`), and
the **rich grid is the on-demand "Maximize" surface**: a lazy-loaded vinci
`detail` table built from the result's columns/rows (basically `starterDsl` with
`chartType: "detail"`).

> **Prerequisite spike.** Install deps and render a `detail` DSL in `VinciViewer`
> to confirm how much **end-user interactivity** the read-only viewer exposes
> (clickable column sort/filter UI vs. designer-only). The spike's result decides
> whether the inline grid gets hand-rolled client sort or also goes through vinci.

## What ships

- **Inline table** (`ResultCard`/`DataTable`): client-side column sort (3-state),
  lightweight column filter / table search, and virtual scrolling + "load more"
  to replace the 1000-row hard truncation. Keep the existing SQL / CSV / Copy /
  endorsed-pill chrome.
- **Fullscreen grid:** wire the **Maximize** button to a modal that lazy-loads a
  vinci `detail` table over the result rows (sort + conditional formatting, and —
  pending the spike — pivot/cross-tab). Reuses `compileSurface`.
- **Kill the dead buttons:** implement or remove **Translate**, the composer
  **cog** / **Auto** picker. (**Share** is implemented in v3.4 — until then,
  remove or hide it rather than leave it inert.)

## Out of scope / deferred

- Editing the grid / chart (→ v3.3, via `@vinci/designer`).
- Server-side pagination for results beyond the in-memory row cap (the truncation
  cap stays; "load more" is client-side over already-fetched rows).
- Pinning a grid into a report (→ v3.4).

## Done when

- [ ] Inline result table supports column sort + filter/search and virtualizes
      large results without the 1000-row cliff.
- [ ] Maximize opens a fullscreen vinci `detail` grid built from the result rows.
- [ ] No inert buttons remain in the thread surface (each is implemented, or
      removed/hidden).
- [ ] Heavy vinci bundle is **not** pulled into the common inline-table path
      (lazy-loaded only when the grid opens).
- [ ] `typecheck` + `lint` + `test` (both apps) + web `build` + agent `smoke` green.
