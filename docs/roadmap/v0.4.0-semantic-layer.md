# v0.4.0 — Semantic layer 📋 Planned

**Theme:** Define metrics once, query them everywhere. A CubeJS-style semantic
model — cubes/entities with measures, dimensions, and joins — that the agent
queries through, so answers use governed, consistent definitions instead of
re-derived ad-hoc SQL.

## Goal & why

With live warehouses (v0.3) the agent writes raw SQL straight against physical
tables. That's flexible but fragile: "revenue," "active customer," or "churn" gets
re-derived — and subtly re-defined — on every question, joins are re-guessed, and
there's no single source of truth. A **semantic layer** captures those definitions
once, declaratively: **measures** (aggregations), **dimensions** (attributes),
**joins** (relationships), and named, **endorsed** metrics built on them. The agent
then issues a _semantic query_ (pick measures + dimensions + a time grain +
filters) and the layer compiles correct SQL — so answers are consistent,
explainable, and trustworthy. This is the thin "endorsed catalog" idea that v0.3
deferred, promoted to a real modeling layer in the spirit of CubeJS.

## Scope

- **Declarative model (cubes)** — a typed, hand-authored model of cubes/entities,
  each mapping to a table or base SQL, carrying:
  - **measures** — `count` / `sum` / `avg` / `count-distinct` / ratio, with types
    and display formatting;
  - **dimensions** — categorical / temporal / numeric attributes (a temporal
    dimension supports time grains: day / week / month / …);
  - **joins** — declared relationships + cardinality between cubes, so the
    compiler can traverse them;
  - **named metrics** — canonical, reusable definitions built from measures, the
    unit a user/agent actually asks for.
- **Query → SQL compiler** — given a semantic query (measures, dimensions, time
  dimension + granularity, filters, order, limit), generate correct **read-only**
  SQL for the active connector (v0.3), resolving the needed joins automatically.
  The compiled SQL still passes through `assertReadOnly`.
- **Agent integration** — new tools (`list_metrics` / `describe_model` /
  `query_semantic`) so the agent **prefers the model**: it discovers the available
  cubes/measures/dimensions and issues a semantic query when a definition fits,
  falling back to raw `run_sql` for the long tail the model doesn't cover.
- **Endorsed surfacing** — mark cubes/metrics **endorsed**; expose that to the UI
  so a `ResultCard` can show "answered from a trusted definition" (the existing
  `Pill` primitive).
- **Model authoring & validation** — decide where the model lives (a typed config
  / files), validate it (unknown column, dangling join, duplicate name), and map
  it onto both the seeded SQLite sample and a Postgres connection.

## Out of scope

- **Pre-aggregations / materialized rollups & caching** (CubeJS's performance
  layer) — correctness first; performance is an icebox follow-up.
- A **visual model builder / UI** — author the model in code for now.
- **Governance depth** — lineage, row-level security, model versioning/approval
  workflows.
- **Auto-generating the model** from `information_schema` — introspection-assisted
  authoring can come later; start hand-authored.

## Technical notes

- Build on the **v0.3 connector seam**: the compiler emits SQL for the active
  connector's dialect — keep dialect differences small and centralized (the SQLite
  sample stays the no-setup default; Postgres is the real target).
- Keep the model a **typed config first** (cubes / measures / dimensions / joins as
  data the tools read), CubeJS-like but minimal — don't build a DSL/parser yet.
- The semantic layer **never bypasses** the read-only guard: `assertReadOnly` runs
  on the compiled SQL exactly as it does on hand-written queries.
- Reuse the existing **result cards** (the v0.1 `ResultCard`; richer variants land
  in v0.5) — a semantic query returns the same result shape the UI already maps, so
  rendering is free.
- Extend `npm run smoke` (and, by v1.0, real tests) to cover the compiler: a known
  semantic query should compile to expected SQL and run against the seeded sample.

## Done when

- A curated model exists (cubes + measures + dimensions + joins) over the sample
  data, and works against a Postgres connection.
- Asking _"monthly revenue by region"_ makes the agent issue a **semantic query**
  that the layer compiles to correct SQL via the model — not hand-written SQL — and
  streams a result card.
- A metric can be marked **endorsed**, and the UI shows the answer came from a
  trusted definition.
- Raw `run_sql` still works as the fallback for questions the model doesn't cover.
